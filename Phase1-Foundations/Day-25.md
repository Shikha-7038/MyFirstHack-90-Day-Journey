## 📚 What I Learned

### 🔵 TCP — Transmission Control Protocol

TCP is a **connection-oriented** protocol.

Before data is exchanged, TCP establishes a connection using a **three-way handshake**:

```text
Client → SYN
Server → SYN-ACK
Client → ACK
```

The main TCP flags I learned to recognize are:

| Flag | Meaning |
| :--- | :--- |
| **S** | SYN — starts a TCP connection |
| **S.** | SYN-ACK — server responds to SYN |
| **.** | ACK — acknowledgement |
| **F** | FIN — connection closes normally |
| **R** | RST — connection is reset |

TCP provides reliability using mechanisms such as:
* Sequence numbers
* Acknowledgements
* Retransmission
* Connection management

Because of this, TCP is commonly used when reliable delivery is important.

#### Examples of TCP usage
* 🌐 Web communication
* 📧 Email
* 📁 File transfers
* 🔐 Many HTTPS connections

---

### 🟠 UDP — User Datagram Protocol

UDP is **connectionless**.

Unlike TCP, UDP does not perform a three-way handshake before sending data. It is designed to have lower overhead and lower latency. UDP does not provide the same built-in reliability mechanisms as TCP.

#### Examples of UDP usage
* 🌐 DNS queries
* 🎮 Online gaming
* 📞 Voice communication
* 📺 Some video and streaming applications

#### The most important difference I understood today
* **TCP** focuses more on reliable delivery.
* **UDP** focuses more on speed and lower overhead.

## 🧪 Practical Work — Capturing Real Network Traffic

I wanted to see whether the concepts I learned actually appeared in real network traffic. I used two approaches.

### 🦈 Method 1 — Wireshark

Wireshark provides a graphical way to capture and inspect packets. I used it to observe traffic generated by my own computer and looked at information such as:
* Source IP
* Destination IP
* Protocol
* Source port
* Destination port
* TCP flags
* DNS traffic

This helped me understand that network communication isn't just something explained in theory. My laptop was continuously generating and receiving packets.

### 💻 Method 2 — Windows Pktmon

Because I am using Windows, I also used Pktmon, which is built into Windows.

I started the capture using:
```cmd
pktmon start -c
```

After allowing the computer to capture traffic, I stopped it using:
```cmd
pktmon stop
```

Then I converted the `.etl` capture into readable text:
```cmd
pktmon format PktMon.etl -o capture.txt
```

The capture produced: `Events formatted: 312201`

This showed that even a relatively short capture could contain a very large amount of packet/event information.

## 🔄 TCP vs UDP — What I Understand Now

| Feature | TCP | UDP |
| :--- | :--- | :--- |
| **Connection** | Connection-oriented | Connectionless |
| **Handshake** | Uses a three-way handshake | No three-way handshake |
| **Reliability** | Reliable delivery | No built-in delivery guarantee |
| **Acks** | Uses acknowledgements | No TCP-style ACK mechanism |
| **Sequencing** | Uses sequence numbers | No TCP-style sequencing |
| **Overhead** | More overhead | Lower overhead |
| **Example** | HTTPS / Web Applications | DNS Queries |

### 🧠 My understanding
TCP and UDP aren't just theory — they determine how real network conversations are carried between systems.
