# Day 32 — Reading Packets with Wireshark

## 🎯 Objective

Today's goal was to move from **recognising packets** to **reading packets in context**.

Instead of looking at individual packets separately, I learned how to follow a complete TCP conversation, understand the TCP lifecycle, observe TLS communication, identify normal background traffic, and start building a baseline for detecting unusual network behavior.

---

## 🧠 Recognising vs Reading Packets

### Recognising packets

Recognising means identifying what an individual packet represents.

Examples:

- `SYN` → starts a TCP connection
- `SYN-ACK` → responds to a connection request
- `ACK` → acknowledges received information
- `FIN` → gracefully closes a connection
- `RST` → abruptly resets a connection

### Reading packets

Reading means understanding packets **in relation to one another**.

For example:

```text
SYN
 ↓
SYN-ACK
 ↓
ACK
 ↓
Data Transfer
 ↓
FIN
 ↓
ACK
```

This sequence tells the story of a TCP conversation rather than just identifying individual packets.

---

# 🤝 Following a TCP Conversation

A TCP conversation has three main stages:

1. Opening
2. Data transfer
3. Closing

---

## 1. Opening — Three-Way Handshake

A TCP connection normally begins with a three-way handshake.

```text
Client → Server     SYN
Server → Client     SYN-ACK
Client → Server     ACK
```

### SYN

The client requests a TCP connection.

### SYN-ACK

The server responds to the request and acknowledges the client's SYN.

### ACK

The client acknowledges the server's response.

After this sequence, the TCP connection is established.

---

## 2. Middle — Data Transfer

After the TCP connection is established, data can be exchanged between the client and server.

For an HTTPS connection, TLS is used to protect the communication.

A simplified flow is:

```text
TCP Handshake
      ↓
TLS Handshake
      ↓
Encrypted Application Data
```

Even when the application data is encrypted, Wireshark can still show useful information such as:

- Source IP
- Destination IP
- Source port
- Destination port
- Packet length
- Packet timing
- Direction of traffic
- TCP information
- TLS information

The contents may not be readable, but the **communication pattern is still visible**.

---

## 3. Closing — TCP Teardown

A TCP connection can close gracefully using `FIN` and `ACK`.

A simplified example is:

```text
FIN
 ↓
ACK
 ↓
FIN
 ↓
ACK
```

A connection can also terminate abruptly using:

```text
RST
```

### RST

`RST` means the TCP connection was reset.

An RST packet does **not automatically mean an attack**. It can occur for legitimate reasons, such as a service refusing a connection or an application cancelling a connection.

The context surrounding the RST is important.

# 🔐 TLS 1.3 Observed in Wireshark

During the practical, I followed one TCP stream and observed **TLS 1.3** traffic.

The stream contained:

- `Client Hello`
- `Server Hello`
- `Change Cipher Spec`
- `Application Data`

### Client Hello

The client begins the TLS negotiation and provides information about the TLS capabilities it supports.

### Server Hello

The server responds and selects parameters for the secure connection.

### Change Cipher Spec

In a TLS 1.3 capture, `Change Cipher Spec` can appear as a compatibility-related message during the handshake.

### Application Data

After encryption is established, application communication is protected.

The actual application data was not readable because it was encrypted.

# 🖥️ Background Network Traffic

One important observation from today's practical was that my laptop continued generating network traffic even when I was **not actively browsing**.

This background activity can be generated by:

- Operating-system services
- Applications
- Network discovery
- Time synchronization
- Updates
- Cloud synchronization
- Other background services

This is sometimes described as **background chatter**.

Understanding this traffic is important because a security analyst needs to know what normal activity looks like before trying to identify abnormal activity.

---

# 📊 Building a Network Baseline

A **baseline** is an understanding of what normal network activity looks like for a device or environment.

A normal communication pattern might look like:

```text
DNS
 ↓
TCP
 ↓
TLS/HTTPS
 ↓
Application Data
```

along with other background network activity.

The exact traffic will vary depending on the device, applications, network, and user activity.

### Important principle

> **You can't reliably identify abnormal traffic until you understand normal traffic.**

Once normal behavior becomes familiar, unusual behavior becomes easier to notice.

---

# 🔎 Important Wireshark Fields

A few fields can provide a large amount of useful information when reading a packet capture.

## TCP Flags

| Flag | Meaning |
|---|---|
| `SYN` | Starts a TCP connection |
| `ACK` | Acknowledges received information |
| `FIN` | Gracefully closes a connection |
| `RST` | Abruptly resets a connection |
| `PSH` | Pushes data toward the application |

TCP flags can be thought of as the **verbs of a TCP conversation** because they describe what the packet is trying to do.

---

## Source and Destination Ports

Ports help identify the service involved in a connection.

| Port | Common Use |
|---:|---|
| `53` | DNS |
| `22` | SSH |
| `443` | HTTPS |
| `3389` | RDP |

A high-numbered source port is often normal because clients commonly use temporary or ephemeral ports.

Therefore:

> **A high port by itself does not mean something is suspicious.**

Context is important.

---

## Time

Packet timing can reveal patterns that may not be obvious from packet contents.

For example:

```text
10:00:00
10:01:00
10:02:00
10:03:00
```

Regular communication at precise intervals may indicate automated behavior.

However:

> **Regular timing does not automatically mean malicious activity.**

Legitimate applications can also communicate periodically.

---

## Packet Length

Packet length shows the size of each captured packet.

A sequence of larger packets can indicate substantial data transfer, while small packets repeated at regular intervals can represent periodic communication or keepalives.

Packet size should always be considered together with other information.

---

## Info Column

The **Info** column provides a quick summary of what Wireshark identifies in each packet.

Examples include:

```text
[SYN]
[SYN, ACK]
Client Hello
Server Hello
Application Data
[FIN, ACK]
```

Reading the Info column can be one of the fastest ways to understand a capture before opening individual packet details.

# 🔬 Follow TCP Stream

One of the most useful Wireshark features practiced today was:

**Right-click a TCP packet → Follow → TCP Stream**

This isolates packets belonging to one TCP conversation.

In the practical, Wireshark showed:

```text
tcp.stream eq 13
```

The selected conversation contained packets:

```text
310–319
```

This resulted in:

**10 packets**

The stream contained TLS 1.3 traffic including:

- Client Hello
- Server Hello
- Change Cipher Spec
- Application Data

The Follow TCP Stream window displayed encrypted data as unreadable characters and symbols because the communication was protected by TLS.

I found TCP traffic and selected a TCP conversation associated with HTTPS traffic.

**Right-click → Follow → TCP Stream**

```text
tcp.stream eq 13
```

The selected stream contained packets:

```text

```

Total:


## Step 4 — Read the TLS Conversation

Within the selected stream, I observed:

```text
Client Hello
Server Hello
Change Cipher Spec

```

The application data appeared encrypted and was not readable as normal text.

This demonstrated that even though the content was encrypted, Wireshark could still show the communication structure and metadata.

---

## Step 5 — Check for RST Packets

I used the display filter:

```text
tcp.flags.reset == 1
```

### Result

**No RST packets were found.**

Therefore:

> **RST packets observed: 0**

This only describes the capture I performed. It does not mean that RST packets never occur on my machine.

---

## Step 6 — Find TCP Connection Attempts

I used the display filter:

```text
tcp.flags.syn == 1 && tcp.flags.ack == 0
```

This searches for SYN packets where ACK is not set, representing the initial packet of a TCP connection.

I found **3 rows**:

```text
57
59
310
```

Therefore:

> **TCP connection attempts observed: 3**

Packet `310` was also the beginning of the TCP stream I followed.

# 🛡️ Reading Packets for Security

Packet reading is the foundation for identifying suspicious network behavior.

Once normal traffic is understood, analysts can begin looking for patterns that do not fit the baseline.

## 🔍 Port Scanning

A possible port scan may look like:

```text
One source
    ↓
Many destination ports
    ↓
Many SYN packets
    ↓
Many RST responses
```

The important pattern is repeated connection attempts across many ports.

---

## 🌐 Suspicious DNS

Potentially suspicious DNS behavior can include:

- Unusually long domain names
- Random-looking domain names
- Unusually high DNS volume

For example:

```text
x7f3k9q2bv.example.com
```

could look machine-generated.

However:

> **A random-looking domain does not automatically mean malware.**

It must be investigated in context.

---

## 📡 Beaconing

A possible beacon can appear as:

```text
Same destination
      +
Small connections
      +
Very regular timing
```

For example, a device communicating with the same external IP every 60 seconds may deserve investigation.

Again, this is a **pattern to investigate**, not automatic proof of malware.

---

## 🔓 Plaintext Exposure

If sensitive information is visible in plaintext where encryption should normally be used, it can indicate a security weakness.

The key security principle is:

> **Sensitive information should be protected when travelling across an untrusted network.**

---

# 🧠 Key Lessons

- Recognising packets means identifying individual packet types.
- Reading packets means understanding their sequence and context.
- A TCP conversation has an opening, middle, and closing.
- `SYN → SYN-ACK → ACK` establishes a TCP connection.
- `FIN` is used for graceful TCP termination.
- `RST` represents an abrupt reset.
- TLS encrypts application communication.
- Encrypted traffic is still visible as network metadata and communication patterns.
- A computer can generate network traffic even when the user is not actively browsing.
- `Follow TCP Stream` isolates one TCP conversation from a larger capture.
- TCP flags, ports, timing, packet length, and the Info column are important when reading traffic.
- A traffic baseline helps identify activity that does not fit normal behavior.
- Security analysis depends heavily on understanding normal traffic first.

---

# 💡 Final Takeaway

> **Don't just look at packets. Read the conversation they create.**

Day 31 was about **recognising packets**.

Day 32 was about **reading packets in context**.

By following a TCP conversation, observing TLS communication, checking TCP flags, and studying background traffic, I started building the foundation for identifying abnormal network behavior.

The goal is not to assume that every unusual packet is malicious.

The goal is to understand:

> **What is normal, what is different, and why?**

That is the mindset needed for network security analysis.
